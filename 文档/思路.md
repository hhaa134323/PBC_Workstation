## 二、选题与痛点

**选题**：IPO 审计 PBC（Provided by Client，客户提供资料）智能管理工作站

**核心痛点**：初级审计员在 PBC 管理上高度依赖手工——收资料、分拣、命名、归档、更新 Excel 状态。环节重复、易错、跨人跨系统。

**SOP 依据**：公司已有《IPO 审计项目 PBC 完整性检查标准作业程序》（AUD-SOP-PBC-01 V1.0），明确定义了角色、流程、状态、异常处理。本产品是 SOP 的"AI 原生 + 双击即用"实现。

---

## 三、竞品分析

**竞品**：Melody 团队"PBC 文件核对工具"（Flask 本地 Web，端口 5001）

**竞品已落地能力**：
| 能力 | 表现 |
|---|---|
| 需求清单自动生成 | 按会计科目勾选（A/C/K1/L1/L2/M/N...） |
| 文件-需求自动匹配 | 智能模式 + AI 辅助模式，带进度条 |
| 多公司智能归属 | Y/N 矩阵视图，9 家公司并列 |
| 资料整理与归置 | 自动重命名 + 多级目录 |
| 文件在线预览 | Excel/PDF 内嵌 |

**竞品强项**：多公司 Y/N 矩阵视图、AI 匹配进度条、文件预览

**竞品盲点**：
1. 流程到"匹配成功"就停，**没有 Senior 复核工作流**（SOP §5.4）
2. **没有完整性检查**（SOP §5.2 期间连续性）
3. 没有风险洞察（SOP §6 异常处理）
4. 只服务 Staff 单角色，**没有 Senior/Manager 视角**（SOP §3）

## 四、差异化定位（乔布斯式双重跳跃）

### 4.1 两轴矩阵

|  | 需配置/培训（左） | 双击即用（右） |
|---|---|---|
| **AI 原生（上）** | 通用审计 SaaS 平台 | **我们（目标，空白象限）** |
| **规则/手动（下）** | 纸质流程 | Excel 手工核对 |

**Melody 竞品位置**：中间偏下（规则为主 + 中易用）

### 4.2 双重跳跃策略

iPhone 式双重跳跃——同时跳两个维度：
- **上推智能化**：AI 原生（LLM 分类、AI 置信度标红、缺口模式识别、替代程序建议）
- **右推易用性**：双击即用（单一输入、零配置、按流程走）

**差异化不是"功能多"，是"两个维度都做到极端"。形态不是差异化核心，A+F 功能价值才是。**

### 4.3 差异化双支柱

- **支柱 A · 三角色协作工作台**：竞品只服务 Staff 单机分拣，我们服务整个审计团队（Staff/Senior/Manager 三视角）
- **支柱 F · 缺料风险雷达**：竞品把 PBC 当操作问题（收齐就完了），我们把 PBC 缺口当审计风险信号
- **环节 5 · 风险化解助手**：F 的行动层，基于缺口做影响分析+替代程序建议+升级汇报

## 五、基于 SOP 的产品思路（核心）

以"一份 PBC 资料的完整生命周期"为主线，5 环节贯穿。

### 5.1 五环节流程

| 环节 | 名称 | SOP 对应 | 差异化定位 |
|---|---|---|---|
| 1 | 客户共享文件夹（输入） | §5.1 资料接收 | 非差异化（地基） |
| 2 | AI 智能处理 | §5.1-5.5 | 地基 + **藏差异化（完整性检查）** |
| 3 | 三角色协作审阅 | §3 + §5.4 | **差异化支柱 A** |
| 4 | 缺料风险雷达 | §6 异常处理 | **差异化支柱 F** |
| 5 | 风险化解助手 | §6 替代程序 | F 的行动层（化解风险） |

**闭环**：环节 5 化解风险后，客户补料重新进入环节 1，形成自我循环。

### 5.2 环节 2 详解（AI 智能处理）

| 子功能 | SOP 条款 | 说明 |
|---|---|---|
| 识别归类 | §5.1 | 判断基础资料 vs 穿行测试证据，对照清单识别请求项 |
| **完整性检查** | §5.2 | **清单覆盖率 + 期间连续性（三年一期有无断档）** |
| 状态标记 | §5.3 | 自动回写 Excel 状态列 |
| 文件归档 | §5.5 | 命名（编号_描述_期间_版本.pdf）+ 目录（/General_PBC/01_历史沿革/） |

**关键差异化**：§5.2 的"期间连续性检查"是 AI 强项——读文件内容判断期间覆盖，Melody 完全没碰。本次做简单版（文件名/元数据判断）。

### 5.3 环节 3 详解（三角色协作审阅）

> v0.5 修订（2026-07-20）：从"按角色聚焦"改为"按任务状态聚焦"。
> 原因：审计员不是固定身份（早上做收料下午做复核晚上做汇报很常见），强制"切角色 tab"是认知负担；
> 且小团队可能 2 人兼任多角色，"角色"概念尴尬。
> **改为按"任务状态"自然聚焦——用户看的是"待办事项"不是"角色视角"，但实际工作流不变。**

严格映射 SOP §3 角色职责。**界面设计**：不是 Staff页/Senior页/Manager页 三选一切换，也不是"按角色 tab"，而是**按任务状态 tab 自然聚焦**——4 个任务状态作为顶部导航（待初检/待复核/超期未提供/已完成），用户点哪个 tab 就看哪个状态的事项。三种角色自然分流（收料的人常驻"待初检"、复核的人常驻"待复核"、监督的人常驻"超期未提供"），但**不强制切换角色身份**。

#### 5.3.1 SOP §3 角色职责（保留作业务参考，但不在界面体现）

**Staff（5 项职责）**：
1. 接收客户 PBC 资料
2. 执行初步完整性检查（清单覆盖率、基本格式、期间连续性）
3. Excel PBC 清单更新状态
4. 资料存入指定文件夹并建立超链接
5. 对"未提供/异常"项标记并初步跟进

**Senior（4 项职责）**：
1. 复核 Staff 的完整性检查结果
2. 确认资料满足底稿要求（签字盖章、版本正确性、数据勾稽、样本代表性）—— 4 维度复核
3. 批准状态更新为"已提供"
4. 解决复杂/争议性资料缺失，决定替代程序

**Manager/Partner（3 项职责）**：
1. 监督整体 PBC 进度
2. 协调重大资料缺失的客户高层沟通
3. 审批关键事项豁免/特殊处理

#### 5.3.2 4 个任务状态 tab 设计（v0.5 新增）

**Tab 1：待初检**（资料刚到，等人确认）
- 顶部：扫描新文件大按钮 + AI 处理进度条（4 步：解析→分类→归档→回写）
- 主区：低置信度项标红置顶 + 置信度进度条 + AI toast 区
- 操作：标记初检完成 → 推到"待复核"
- 自然使用者：收资料的人（Staff 职责）

**Tab 2：待复核**（已初检，等高级审计员复核）
- 顶部：4 维度复核清单（签字盖章/版本正确性/数据勾稽/样本代表性）
- 主区：置信度低的项置顶（红色高亮提醒）+ 已有 AI 影响分析摘要
- 操作：通过 → 推到"已完成" / 退回 → 推回"待初检" + 触发风险化解
- 自然使用者：做复核的人（Senior 职责）

**Tab 3：超期未提供**（风险雷达识别的缺料项）
- 顶部：总体进度仪表盘（已收/待审/超期）
- 主区：风险热力图（实体×科目）+ 高风险项列表 + AI 影响分析
- 操作：点击高风险项 → 弹风险化解卡片 → 采纳替代程序 / 收升级汇报包一键复制
- 自然使用者：监督进度的人（Manager 职责）

**Tab 4：已完成**（终态归档）
- 顶部：总体完成率
- 主区：已归档文件列表（按实体分组）+ 状态历史日志
- 操作：查看详情/撤销归档
- 自然使用者：所有人

#### 5.3.3 设计原则

- **不提角色身份**：用户点 tab 是看"我有啥活要干"，不是"我是啥角色"
- **自然分流**：实际工作流里，收料的人常驻 Tab 1，复核的人常驻 Tab 2，监督的人常驻 Tab 3——三种角色自然分流
- **一人兼多角色无障碍**：审计员早上做 Tab 1、下午做 Tab 2、晚上做 Tab 3，无切换认知负担
- **小团队友好**：2 人兼任多角色完全无影响
- **工作流连续**：4 个 tab 是同一条链路的状态推进，不是三个独立视角
- **AI 元素按状态自然分布**：Tab 1 有置信度+进度条+toast、Tab 2 有 AI 复核提示、Tab 3 有化解卡片+热力图——AI 元素不重复，按状态自然出现

#### 5.3.4 类比

- GitHub Issues：没有"你是 Maintainer/Contributor 切换"，只有 Open/Closed tab
- Linear/Notion 任务板：没有"你是 Manager 切换"，只有 In Progress/Review/Done 状态列

### 5.4 环节 4 详解（缺料风险雷达）

**SOP 依据**：§6 异常处理机制
- **超期阈值 = SOP 规定的"5 个工作日"**（非拍脑袋）
- SOP 原文："关键 PBC 超过 5 个工作日仍未提供，向 Senior 汇报"
- 我们的雷达 = §6 异常处理的自动化呈现 + 升级触发

**功能**：
- 超期自动识别（按 5 工作日阈值）
- 缺口模式反推审计风险热点（如存货科目迟迟收不齐 → 可能存货有问题）
- Manager 视角的项目风险热力图

### 5.5 环节 5 详解（风险化解助手）

**SOP 依据**：§6 异常处理（替代程序）+ §5.4 Senior 职责（决定替代程序）

**为什么不做催办**：催办针对客户、方式多样、每个项目不一样、无法统一化、AI 价值低。

**风险化解助手的三条化解路径**：

| 路径 | 说明 | 示例 |
|---|---|---|
| ① 影响分析 | 缺口→影响哪些审计科目/结论 | 存货盘点表缺失 → 影响存货科目期末余额审计结论 |
| ② **替代程序建议**（核心） | AI 基于资料类型+审计准则知识库，推荐替代审计程序 | 银行流水缺失 → 建议执行银行函证+检查对账单+核对网银 |
| ③ 升级汇报包 | 超阈值自动生成给 Senior/Manager 的结构化汇报 | 哪些超期、影响哪些科目、建议关注等级 |

**为什么比催办好**：SOP 依据强（§6）、可统一化（审计准则有标准）、AI 价值高（知识库+推理）、有审计深度、不依赖客户。**这是 AI 价值最高的环节**。

## 六、状态机（SOP §4.2 贯穿全工作台）

### 6.1 四状态定义

| 状态 | 颜色 | 定义 |
|---|---|---|
| 未提供 | 红色 | 截止日到未提供，或严重缺失 |
| 已提供，审核中 | 深绿 | 已收到并整理，等 Senior 复核 |
| 已提供 | 浅绿/灰 | 终态，Senior 复核通过，已归档 |
| 不适用 | 灰色 | 不涉及公司情况 |

### 6.2 状态流转

```
未提供 ──(Staff 初检)──→ 已提供，审核中
                              │
                  ┌───────────┴───────────┐
                  │                       │
            (Senior 通过)          (Senior 不通过)
                  │                       │
                  ▼                       ▼
              已提供              退回"未提供"

不适用（独立状态，需备注理由）
```

Excel 中通过条件格式自动着色，限制状态列只能输入这四个选项（数据验证）。

## 七、统一的 PBC 清单表格

**不再使用两个 Excel，统一成一个标准表格。** SOP §4.1 原定义两个文件（基础资料长表 + 穿行测试宽表），现简化为**一个 Excel 文件、一个 Sheet、长表结构**——每行一个资料项，用列区分类型和归属。这更符合"双击即用"（一个表比两个表简单）。

### 7.1 统一表格字段设计

字段对齐实际 PBC 清单文件（pbc_list-1.xlsx）+ 扩展产品需要的字段：

| 列名 | 来源 | 说明 | 示例 |
|---|---|---|---|
| 一级分类 | 实际文件 | 资料大类 | 历史沿革 |
| 二级分类 | 实际文件 | 资料编号 | 历-1 |
| 相关科目 | 实际文件 | 基本资料/货币资金/固定资产等 | 基本资料 |
| 资料名称 | 实际文件 | 资料名称，AI 匹配依据 | 股权架构图 |
| 问题/需求描述 | 实际文件 | 详细需求描述 | 请提供贵集团各公司的股权架构图... |
| 报告期间 | 实际文件 | 覆盖期间 | 2023/12/31-2025/12/31 |
| 实体归属 | **扩展** | 公司级（具体公司名）/ 集团级 | 集团合并 / ABC科技 |
| 状态 | 实际文件 | 四状态之一 | 已提供，审核中 |
| 置信度 | **扩展** | AI 匹配置信度 | 0.92 |
| 文件路径 | 实际文件 | 归档后填入 | 集团合并/股权架构图.pdf |
| 备注 | 实际文件 | 异常记录 | AI 匹配置信度高 |

### 7.2 资料粒度区分（用"实体归属"列处理）

资料有两种粒度，用"实体归属"列区分：

| 资料粒度 | 例子 | 实体归属列填法 |
|---|---|---|
| **公司级** | 子公司银行流水、某账套明细账 | 具体公司名（如 ABC子公司A） |
| **集团级/合并级** | 合并明细账、集团章程、合并报表 | "集团合并" |

### 7.3 矩阵视图（前端动态生成）

原来宽表的"实体_年份矩阵"视图不丢——**在前端从长表数据动态透视生成**。用户想看矩阵时，前端按"实体归属×报告期间"聚合状态，实时渲染 Y/N 矩阵。数据存储用统一长表，展示用动态矩阵，两全其美。

测试用 ABC 公司（3 家子公司 + 1 个集团合并），既简单又能覆盖两种粒度。

## 九、产品形态（从差异化推导）

**形态不是独立选择，是从"双击即用 + 无技术背景用户 + Windows + 最低成本"约束推导的结果。**

### 9.1 推导过程

| 约束 | 推导 |
|---|---|
| 必须双击即用 | 不能要用户装 Python/装依赖/配环境 |
| Windows 最低成本 | 打包成 .exe，双击运行，自带运行环境 |

### 9.2 形态选择

**打包成 exe 的本地应用**：HTML + FastAPI + PyInstaller

- **前端**：HTML + Alpine.js（单页 Web，三角色统一界面）
- **后端**：FastAPI 本地服务（127.0.0.1）
- **打包**：PyInstaller 打包成单 exe，用户双击即用
- **输入**：客户指定的共享文件夹（单一入口）
- **数据**：全程模拟数据，ABC 公司、覆盖全状态

### 9.3 为什么选这个形态（对比）

| 形态 | 双击即用 | 文件操作 | UI 体验 | 14天风险 | 选不选 |
|---|---|---|---|---|---|
| HTML+FastAPI+pyinstaller | ✅ 双击 exe | ✅ | ✅ 现代Web | 低 | **选** |
| Streamlit+pyinstaller | ✅ | ✅ | ⚠️ 朴素 | 低 | 备选 |
| PyQt5 桌面 GUI | ✅ 真窗口 | ✅ | ⚠️ 桌面风格 | 高 | 不选 |
| Dify/Coze 低代码 | ✅ 在线 | ❌ 受限 | ⚠️ | 中 | 不选 |

## 十、技术架构（5 层）

| 层 | 内容 | 说明 |
|---|---|---|
| 第 1 层 · 用户层 | 双击 PBC工作站.exe → 自动打开浏览器 | 无需装 Python/依赖 |
| 第 2 层 · 前端层 | 单页 Web 应用（HTML/CSS/JS + Alpine.js） | 三角色统一界面，信息区块按角色聚焦 |
| 第 3 层 · 后端层 | FastAPI 本地服务（127.0.0.1） | API + 业务逻辑 + 文件操作 + Excel 读写 + 调度 AI |
| 第 4 层 · AI 能力层 | LLM API（可选配置）+ 审计知识库 | 分类识别、完整性检查、置信度评估、替代程序建议 |
| 第 5 层 · 数据/文件层 | 共享文件夹 + PBC Excel + 归档目录 | 输入/状态/输出三处文件 |

### 10.1 AI Agent 核心逻辑（感知-思考-行动-人确认）

AI Agent 不是简单调 API，是"感知-思考-行动-人确认"的循环：

- **环节 2**：感知（扫描文件夹新文件）→ 思考（LLM 识别+匹配+期间检查+置信度）→ 行动（命名+归档+Excel回写）→ 人确认（Staff 确认/纠正）
- **环节 3**：感知（看所有"审核中"项+置信度）→ 思考（置信度<0.7 标红）→ 行动（Senior 复核区置顶红项）→ 人确认（Senior 通过/退回）
- **环节 5**：感知（风险雷达识别缺口）→ 思考（查知识库+推理替代程序）→ 行动（生成化解建议卡片）→ 人确认（Senior 采纳并记录底稿）

**关键：AI 不替代人判断，是帮人把"最该看的"挑出来。**

## 十二、AI 模型配置（可选，不固定）

**AI 模型设置为可选择，不固定某一个平台或模型。** 用户可在配置文件中设置提供商、API Key、模型名，产品启动时读取配置。

### 12.1 配置方式

在 `config/api_config.json` 中配置（OpenAI 兼容格式，支持百炼/OpenAI/其他兼容平台）：

```json
{
  "ai_provider": {
    "provider": "bailian",
    "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1",
    "api_key": "用户的key",
    "models": {
      "classification": "glm-5",
      "vision": "qwen3-vl-plus",
      "reasoning": "glm-5",
      "embedding": "text-embedding-v4"
    }
  }
}
```

### 12.2 不同任务可配置不同模型

| 任务 | 配置项 | 默认推荐（百炼） | 说明 |
|---|---|---|---|
| 文件内容识别+分类 | classification | GLM-5 | 中文理解强，分类准确 |
| 期间连续性检查（读图） | vision | Qwen3-VL-Plus | 能读 PDF/扫描件图片 |
| 替代程序建议 | reasoning | GLM-5 | 推理能力强 |
| Embedding 检索 | embedding | text-embedding-v4 | 中文语义检索 |

### 12.3 为什么做成可选

- **灵活性**：不同用户/团队可能有不同平台的 API（百炼、OpenAI、私有部署等）
- **可替换**：模型升级换代时，改配置即可，不用改代码
- **降级容错**：某个模型不可用时可切换备用模型

**API Key 配置在本地，不上传任何真实客户数据。**

## 十七、模块拆分与开发策略

### 17.1 为什么拆分

一次性生成全部功能的问题：
1. 上下文爆炸——所有代码堆在一个对话里，后续改一处上下文就不够
2. 维护困难——几千行代码在一个 session 里，牵一发动全身
3. bug 累积——没有逐模块验证，问题层叠

### 17.2 模块拆分（7 个模块）

| 模块 | 内容 | 把握 | 依赖 |
|---|---|---|---|
| **M1 项目骨架** | 目录结构 + 配置 + 入口 + 打包脚本 | 90% | 无 |
| **M2 Excel 读写层** | openpyxl 读写 PBC 清单 + 条件格式 + 状态机 | 85% | M1 |
| **M3 AI 处理层** | LLM 调用 + 文件解析(PDF/Excel) + 分类识别 + 完整性检查 | 75% | M1 |
| **M4 后端 API** | FastAPI 路由 + SQLite + 调度 AI + 文件监听 | 85% | M2, M3 |
| **M5 前端界面** | HTML + Alpine.js + 三角色统一界面 + 矩阵视图 | 80% | M4 |
| **M6 风险雷达+化解** | 超期检测 + 替代程序建议 + 升级汇报 | 80% | M4 |
| **M7 打包 exe** | PyInstaller 打包 + 一键启动脚本 | 85% | 全部 |

### 17.3 上下文管理策略

每个模块用**子 agent 独立开发**（独立上下文，不污染主对话）：

```
主对话（协调层）
  ├── 只做：决策、协调、验收
  ├── 不写：大段代码
  │
  └── 子 agent（独立上下文）
       ├── M1 骨架 → 完成验收 → 封装
       ├── M2 Excel层 → 完成验收 → 封装
       ├── M3 AI层 → 完成验收 → 封装
       ...每个模块独立上下文，不互相污染
```

### 17.4 开发顺序

```
M1 骨架 → M2 Excel层 → M3 AI层 → M4 后端API → M5 前端 → M6 风险雷达 → M7 打包
```

- M1-M2 可先做（不依赖审计员 PBC 清单）
- M3 需要 API Key（已完成）
- M5 前端等后端 API 接口定好再做

### 17.5 每个模块的流程

1. 主对话定义模块接口约定（输入输出）
2. 启动子 agent 开发（独立上下文）
3. 子 agent 完成后返回代码
4. 主对话验收（读关键文件确认）
5. 验收通过 → 该模块"封装"，后续不改
6. 有问题 → 在新的子 agent 上下文里改，不回主对话

## 十九、AI 主动推送设计（暴露已有 AI 能力）

> 版本：v0.4 新增
> 日期：2026-07-20
> 依据：用户反馈"AI 在产品里不够凸显" + 收敛决策"不加新功能，把已有 AI 能力用界面表达"

### 19.1 设计原则

**不加新功能**。AI 主动推送不是新功能，是**把已有的后端 AI 能力主动暴露给用户**。

当前后端 AI 能力都做了（classify_file / check_period_completeness / dashboard / resolve / suggest_alternative_procedures），但都是被动等用户调用。加 toast 是让 AI "主动开口"，让用户看到"AI 在思考"。

### 19.2 5 个推送时机（对应已有后端能力）

| # | 时机 | 触发条件 | AI 推送内容（自然语言） | 后端已有能力 |
|---|---|---|---|---|
| 1 | 文件扫描完成 | watchdog/扫描触发后 | "扫描完成，发现 N 份新文件，已自动分类归档。其中 M 份置信度<0.7，建议人工复核" | ✅ classify_file |
| 2 | 期间检查异常 | AI 发现断档 | ⚠ "这份银行流水覆盖 2025/01-09，缺 10-12 月，建议退回客户补料" | ✅ check_period_completeness |
| 3 | 置信度偏低 | classify_file 返回 conf<0.7 | ⚠ "这份文件 AI 匹配置信度 0.58（偏低），原因：印章模糊。建议人工确认" | ✅ classify_file |
| 4 | 超期阈值 | overdue_days > 5 工作日 | ⚠ "存-4 存货盘点表已逾期 7 天，按 SOP §6 应向 Senior 汇报。点击查看影响分析" | ✅ dashboard 已有 |
| 5 | 缺口模式识别 | 某科目缺料集中 | "本周存货类资料缺料率 80%，可能存在客户拖延，建议提前沟通" | ✅ audit_risk_hotspots |

### 19.3 推送形态（前端）

- 顶部 toast 横条
- 中低优先级：3 秒消失
- 高优先级（⚠ 红色）：常驻置顶，需用户主动 dismiss
- 可点击查看详情（跳到对应 item）
- 可"采纳"/"忽略"

### 19.4 优先级分级

| 级别 | 触发 | 形态 |
|---|---|---|
| 🔴 高（必须看） | 期间断档 / 印章异常 / 超期阈值 | 强制弹+常驻置顶 |
| 🟡 中（建议看） | 置信度低 / 缺口模式 | 弹 3 秒后消失 |
| 🟢 低（FYI） | 扫描完成 / 状态变更 | 静默记录，可点开看 |

### 19.5 实现策略

后端不需要新接口——已有的 `/api/files/task/{id}` 和 `/api/risk/dashboard` 已返回所有需要的信息。前端轮询这些接口后**在前端判断推送条件**。

唯一要加：扫描完成时让 classify_file 返回结果多带 `advisory_note` 字段（自然语言提示列表）。

### 19.6 砍掉的提议（明确不做）

下列功能提议都**不做**，因为不在 A+F 差异化定位内：

| 砍掉的提议 | 不做理由 |

## 二十、安全合规说明（安永 Information Security 通知）

> 版本：v0.4 新增
> 日期：2026-07-20
> 依据：2026-07-20 收到安永 GC Information Security 全员通知《AI 全民编程时代，如何守住安全底线》

### 20.1 通知来源

`D:/AgentProjects/IpoPBC/0/使用提醒.jpg` —— 安永 GC Information Security 发送给 D-D-P-CN-Pers; D-D-P-HK-Pers，抄送 PRC Information Security。

### 20.2 通知 3 条核心要求

1. **警惕"黑盒代码"**：AI 生成代码不能直接部署到生产环境或客户系统，必须人工 Code Review + 隔离测试
2. **严守"数据红线"**：只用安永授权 AI 工具；仅向 AI 提供完成任务所需的最小必要信息
3. **建立"人机协作"新规范**：人是最终防线；发现 AI 异常立即停止并上报

### 20.3 受影响的功能点（5 项）

| # | 功能 | 风险点 | 当前状态 | 缓解措施 |
|---|---|---|---|---|
| 1 | AI 文件分类（环节 2 classify_file） | 客户文件含敏感信息（账户号等）发给百炼 | 演示用 mock_data 合规 | ① mock 虚构数据 ② 生产用前脱敏 ③ AI 工具可选配置 |
| 2 | 期间检查（环节 2 check_period_completeness） | 同上 | 已截断到 3000 字 | 同上 |
| 3 | 影响分析+替代程序（环节 5 resolve） | 把 item 信息发 AI | item 是审计需求清单非客户机密 | **已合规**（最小必要信息） |
| 4 | Qwen-VL-Plus 视觉兜底（扫描件 OCR） | 扫描件含印章/签字/账户号 | 演示用 mock_data 合规 | 同 1 |
| 5 | AI 生成代码（M1-M6 全部子 agent 产出） | 通知要求 Code Review | 主对话抽样验收（非正式 Review） | 完成所有开发后做正式 Code Review |

### 20.4 不受影响的设计（5 项已有合规设计）

1. **AI 工具可选配置**（思路 12）：产品不固定百炼，用户可切换到任何 OpenAI 兼容平台，包括安永未来授权的其他工具
2. **API Key 本地保存**（思路 12.3）：不上传任何真实客户数据到云端
3. **mock_data 全是虚构**（思路 16.2）：演示用数据完全合规
4. **双击即用本地应用**（思路 9）：所有数据处理在本地 Windows 电脑，不上云
5. **人不被替代**（思路 10.1）：AI 不替代人判断，是帮人把最该看的挑出来

### 20.5 关键发现：通知原则 vs 产品设计原则对照

| 通知要求 | 产品设计 | 评估 |
|---|---|---|
| 只用安永授权 AI 工具 | 思路 12 AI 工具可选配置 | ✅ 用户可切换到授权工具 |
| 最小必要信息 | 思路 16 mock_data 全是虚构 | ✅ 演示用合规 |
| 人是最终防线 | 思路 10.1 AI 不替代人判断 | ✅ 正好符合 |
| AI 代码必须 Code Review | M1-M6 子 agent 写代码，主对话验收 | ⚠️ 完成开发后做正式 Review |

**关键发现**：通知"人是最终防线"原则正好是思路 10.1 的设计原则。**产品差异化定位符合安永安全规范方向**，可作为产品卖点。
